- **2026-11-11, the session** (a proposal until the owner decides). How the module is built where the owner's brief leaves the choice. A part is one call of one method, given reading ends that wait (`Cursor`) and writing ends that only append (`Appender`): a process as a sequential program on waiting reads, so that a part of several inputs chooses what it reads next, and what a part keeps is its call's. A log has no end: a run ends by its context, and the tests' finite data carries its own stop. A topic's description (`Topic[K, V]`) is apart from its logs (`TopicLogs`), which come from outside, so that one part runs on a binding's logs and on memory's. Topics of several schemas are given to a part as a set (`ReadSet`, `AppendSet`) and a partition reached by the topic's typed description, Go having no family of types indexed by a value. Three things the Lean holds by a type or a proof are checked when the working space is made: that a topic to read is clean, that no name is used twice, that each topic's schema has its consumer. A schema's consumer is given with the database its pushes go into (`Database[P]`), and `Warehousing.Run` sends each partition's pushes to the topic's table. The logs in memory are the tests' own, not exported. The table has a row for each structure's field and each inductive's constructor too, the open parts being fields. In the `Makefile`, one recipe checks a module (`go-check`), and `check-lib` checks the library alone. Shapes: `abstract/`, `Makefile`.
